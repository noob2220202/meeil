# 부하 테스트 (M9)

## 방법

`tools/loadtest`: 가상 사용자 N명이 개발용 로그인으로 가입(약관·생년월일·닉네임·지역 보고)한 뒤, 앱 사용 비율을 흉내 낸 요청을 생각 시간(평균 1초, 0.5~1.5초 무작위)을 두고 반복한다.

| 비중 | 요청                  |  비중 | 요청                         |
| ---: | --------------------- | ----: | ---------------------------- |
|   15 | 안 읽은 편지 수       |     5 | 지역 보고                    |
|   12 | 염소 스케줄           |     5 | 출석 달력                    |
|   12 | 받은 편지함           |     4 | 업적                         |
|   10 | 내 정보               |     4 | 닉네임 검색                  |
|   10 | 롤링 탭 요약(세 레벨) |     4 | 편지 맡기기(쓰기, 원장 차감) |
|    6 | 보낸 편지함           | 3+3+2 | 공지·포인트 내역·출석 체크   |

- 가상 사용자마다 다른 `X-Forwarded-For`를 보내 서로 다른 클라이언트로 센다(서버는 프록시 1단 뒤라고 믿는다 — 운영의 Caddy와 같은 조건).
- 업무상 정상인 4xx(염소가 다른 시에 있음, 포인트 부족)는 오류로 세지 않고 따로 센다. 오류 = 5xx·네트워크 오류·시간 초과(10초)·예상 밖 4xx.
- **기준(통과 조건)**: 전체 p95 ≤ 300ms, p99 ≤ 800ms, 오류율 ≤ 0.1%. 기준을 넘으면 종료 코드 1.
- 이 생각 시간(1초)은 실제 앱보다 5~10배 빡빡하다. 앱은 안 읽은 편지 수를 1분마다, 지역을 5분마다, 스케줄을 30분마다 부르고, 나머지는 사람이 화면을 넘길 때만 부른다 → 활동 중인 사용자 1명 ≈ 0.1~0.2 req/s.

```bash
# 서버를 개발용 로그인으로 띄운 뒤(운영 서버 금지 — 운영 도메인이면 도구가 거부)
pnpm --filter @meeil/tools-loadtest load --url http://localhost:3000 --users 500 --seconds 60 [--think 1000] [--out report.md]
```

CI는 매 커밋 100명·20초 스모크를 돌린다(`.github/workflows/ci.yml`).

## 환경

4코어·16GB 한 대에 PostgreSQL 16(Docker), 서버(`node dist/server.js`, 한 프로세스), 부하 발생기를 함께 올렸다. 부하 발생기가 코어 하나 가까이 쓰므로 실제 VPS보다 불리한 조건이다.

## 한계 찾기 (1,000명) — 병목과 고친 것

| 단계                             |    처리량 | 전체 p95 |            오류 | 비고                               |
| -------------------------------- | --------: | -------: | --------------: | ---------------------------------- |
| 처음                             | 334 req/s |  9,584ms | 423 (시간 초과) | 롤링 탭 요약 p50 9.6초             |
| ① 롤링 조회 고침                 | 420 req/s |  2,563ms |               0 | 시간 초과 사라짐                   |
| ② 스케줄 캐시 + 로그 한 줄       | 536 req/s |  1,641ms |               0 | 스케줄 p50 559→8ms                 |
| ②, 워커 3개(`WEB_CONCURRENCY=3`) | 550 req/s |  1,549ms |               0 | 같은 4코어를 부하 발생기와 나눠 씀 |

1,000명·생각 시간 1초는 한 프로세스의 CPU 한계(약 500 req/s)를 넘는 일부러 과한 부하다. PostgreSQL은 연결당 CPU 10% 남짓으로 여유가 있었고, 병목은 서버 프로세스의 CPU였다(프로파일: Prisma 런타임이 바쁜 시간의 약 40%, 로그 쓰기 7%).

**① 롤링 탭 요약** (`GET /rolling/current/all`)

- 세 레벨을 차례로, 레벨마다 쿼리 약 10개(내 지역 2번, 차단 목록, 장, 글, 염소, 지역 이름, 주제…)를 직렬로 실행했다.
- 무엇보다 이번 장을 `upsert`로 가져와 **모든 사용자가 같은 전국 장 행에 쓰기 잠금**을 걸고 줄을 섰다.
- → 먼저 읽고 없을 때만 만들기, 보는 사람 정보(지역·차단)는 요청당 한 번, 세 레벨 병렬, 염소·지역 이름은 10분 메모리 캐시.

**② 염소 스케줄** (`GET /goats/schedule`)

- 모두에게 같은 공개 정보인데 요청마다 정류 수백 개를 읽었다.
- → 30초 칸마다 본문을 나눠 쓰고 `serverTime`만 매번 새로(기기 시계 보정은 그대로).
- 요청 로그는 두 줄(incoming·completed)에서 응답 때 한 줄로(라우트 패턴만, 쿼리 문자열 없음).

**그 밖의 설정**

- DB 연결 풀 크기 `DATABASE_POOL_MAX`(기본 20, 워커당).
- 워커 프로세스 수 `WEB_CONCURRENCY`(기본 1). 배경 작업은 1번 워커만 돌린다.

## 용량 추정과 권장

- 한 프로세스 ≈ 500 req/s(생각 시간 1초 가상 사용자 500명에서 p95 32ms). 실제 사용 패턴(활동 중 0.1~0.2 req/s/명)으로 바꾸면 **동시에 앱을 켜 둔 사람 2,500~5,000명**까지 한 코어로 기준 안이다.
- 비공개 테스트·출시 초기에는 `WEB_CONCURRENCY=1`로 충분하다. 동시 접속이 늘면 VPS 코어 수만큼 올린다. 이때 `워커 수 × DATABASE_POOL_MAX < 100`(PostgreSQL 기본 max_connections)을 지킨다.
- 워커를 늘리면 요청 제한 카운터가 워커마다 따로라 실제 한도가 ×N이 된다. 남용이 보이면 Redis 저장소로 옮긴다(지금은 불필요).
- 다음 병목 후보: 롤링 탭 요약(가장 무거운 읽기, p95 48ms)과 인증의 요청당 사용자 상태 조회(즉시 정지·탈퇴 반영을 위해 일부러 둠).

## 다시 돌릴 때

```bash
docker compose exec -T postgres psql -U meeil -c "CREATE DATABASE meeil_load"
export DATABASE_URL=postgresql://meeil:meeil@localhost:5432/meeil_load
cd apps/server && pnpm -s db:deploy && pnpm -s db:seed && pnpm build
AUTH_DEV_LOGIN=true PORT=3100 node dist/server.js &
cd ../..
pnpm --filter @meeil/tools-loadtest load --url http://localhost:3100 --users 500 --seconds 60
docker compose exec -T postgres psql -U meeil meeil_load < deploy/sql/integrity.sql
```
